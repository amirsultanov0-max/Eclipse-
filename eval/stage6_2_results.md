# Stage 6.2 — capacity at fixed data exposure: results

Analysis date 2026-09-23 (the commit date of the last capacity run). Generated by
`scripts/analyze_stage6_2.py`, which reads only committed files; rerun it with `--verify`
to reproduce this document byte for byte.

Pre-registered in `eval/stage6_2_preregistration.md` (sections 6 and 7, with amendments 1-3).
The question: does raising capacity from 1.77M to 10.54M parameters improve validation loss
under the same 200 MB data and 10,000-step budget?

> **Read the per-run files with this in mind.** Every run summary in `results/stage6_2/`
> states the d128 architecture — *"d_model 128, 4 heads, d_ff 512 ... 1,767,424
> parameters"* — whatever architecture flags the run used, because `train_transformer.py`
> hardcodes that line. **The capacity runs were genuinely d352**: their manifests record
> `d_model 352, n_heads 4, d_ff 1408`, and each checkpoint config records exactly
> 10,537,472 parameters. No number in this analysis comes from that line. Anyone reading a
> run file on its own would be misled; section 8 has the details.

## 6. Observations

**Seed spread: the capacity arm is far noisier across seeds.** Sample SD 0.0369 against 0.0050 on the full file, a factor of 7.4; 0.0370 against 0.0050 on the clean subset, a factor of 7.4. The three capacity runs span 0.0732 nats, 62% of the effect measured in Stage 6.1's data intervention (0.1182 nats) — roughly two-thirds of it. **VERIFIED** (computed from section 3).

Why a wider model varies more from seed to seed is not established here, and three seeds is
a small sample from which to estimate an SD, so the ratio itself is imprecise. Treat it as a
flag for the Stage 6.3 design — noise estimates there should use the larger SD — not as a
measured constant. **INFERRED**

**Best checkpoint.** All three capacity runs selected step 10,000, the last step, as their best checkpoint: confirmed. In the reference arm only 2 of 3 did — `sr_data200mb_s1338` selected step 9,750 (seed 1337: 10,000, seed 1338: 9,750, seed 1339: 10,000) — so 'every run selected the final step' holds for the capacity arm, not for both arms. **VERIFIED** (from the checkpoint recorded in each official eval file).

Selecting the final step means monitoring loss was still falling when the budget ran out, so
**neither arm is trained to convergence**; both are budget-limited at 10,000 steps. A capacity
comparison at a fixed step budget is therefore not a comparison of converged models, and the
larger model has more to gain from a longer budget than the smaller one. **INFERRED**

**Loss by position in the window.** Mean across the three runs of each arm, full file:

| target positions | reference arm (reused) | capacity arm (new) |
|---|---|---|
| 1-16 | 2.8461 | 2.7138 |
| 17-64 | 2.2364 | 2.0604 |
| 65-128 | 2.0897 | 1.9092 |
| 129-256 | 2.0607 | 1.8774 |
| 257-511 | 2.0629 | 1.8769 |

- reference arm (reused): 0.7564 nats from the 1-16 bucket to 65-128, then +0.0289 from 65-128 to 129-256 and -0.0022 from 129-256 to 257-511.
- capacity arm (new): 0.8046 nats from the 1-16 bucket to 65-128, then +0.0318 from 65-128 to 129-256 and +0.0005 from 129-256 to 257-511.

**Both arms flatten after 128-256 tokens.** In each arm the change over the last two buckets
is under 0.01 nats, against roughly 0.8 nats gained over the first 128 positions. Extra
context beyond about 256 tokens buys almost nothing at either capacity. **VERIFIED**
(computed from the per-run position tables). The flattening is a property of these models on
this corpus; it is not evidence about what a longer context would do for a larger model or a
different corpus. **INFERRED**

## 7. Scope and what is not claimed

- **Fixed data exposure, not fixed compute.** Both arms saw 81,920,000 token positions; the
  capacity arm used about 2.5x the compute per step. This says nothing about which model is
  more compute-efficient, or which would win at an equal FLOP budget.
- **One LR policy.** Both arms ran at a constant 1e-3. Whether a different policy changes the
  capacity result is exactly what Stage 6.3 is for.
- **The reference arm was not blind.** Its losses were published before this preregistration,
  so the within-arm SD that feeds the 3x threshold was known when the rule was fixed
  (preregistration section 3).
- **Secondary generation metrics are not reported here.** The Category 2 schema (amendment 3)
  requires a new blind set built from these arms' checkpoints; none has been built yet.
- **n = 3 per arm**, by the stopping rule: three seeds are the complete experiment and no
  further seed is added after seeing these results.

## 8. Known defect in the per-run result files

`train_transformer.py` writes a hardcoded architecture line into every run summary, so each
capacity run's `.md` describes itself as *"d_model 128, 4 heads, d_ff 512 ... 1,767,424
parameters"*. That line is wrong for these runs. The runs really were d352: the manifests
record `d_model 352, n_heads 4, d_ff 1408`, each checkpoint's config records exactly
10,537,472 parameters, and the driver refused to commit a run whose parameter count differed.
No number in this document comes from that line. **VERIFIED**

The defect is in the summary text only, not in what was trained or evaluated. Fixing it edits
a file frozen by preregistration section 9, so it is left for a documented amendment before
Stage 6.3 rather than changed silently now.
